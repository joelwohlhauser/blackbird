# Issues

Keep the team's issue tracker current in the background. The team instructions name the tracker and its states. Without a tracker, skip all of this.

- **Create one by default.** When the work has no issue yet, create it at Branch. Skip it when the user says so ("no issue") or picked that in the interview.
- **Use its branch name.** Use the tracker's suggested branch name exactly.
- **Move the state with the work:**
  - filed for later, such as a sidequest: the backlog state,
  - work starts at Branch: the in-progress state, assigned to the current user,
  - Ship is done: the done state.
- **Don't fight the integration.** When the tracker's GitHub integration already moves the issue on pull request events, only check that it did.
- **Keep the description short.** One plain paragraph about the problem, in product terms. Update it when the brief changes. No investigation logs, file names, or checklists; the pull request holds the details.
- **Link both ways.** The pull request mentions the issue, and the issue links the pull request.
